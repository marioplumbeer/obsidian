# The Ten Commandments of Maintaining Legacy Code

## Summary
David Anderson frames legacy code maintenance as a discipline with explicit rules, borrowing the "commandments" structure to argue for respecting prior engineering work and refusing to let short-term pressure degrade a system. This note captures only the first two of ten commandments — the rest are behind Scarlet Ink's paid subscription and weren't accessible.

Source: [The Ten Commandments of Maintaining Legacy Code — Scarlet Ink](https://www.scarletink.com/the-ten-commandments-of-maintaining-legacy-code/) (David Anderson, 18 May 2026)

---

## Decisions & insights

### 1. Thou shalt not lament nor cry out against the code
Legacy code exists because it succeeded — it survived because it delivered customer value. Anderson cautions against emotionally judging the engineers who came before: "we don't know the inputs that created our current situation." The fix is factual recognition of problems while assuming prior engineers had good intentions, even under constraints like being overworked or underfunded.

### 2. Thou shalt not suffer tight schedules to befoul thy system
Don't sacrifice code quality to hit a deadline. Anderson argues there are always alternatives — cut features, extend the timeline, add resources — and warns that "just this once" becomes routine, making the system progressively harder to maintain over time.

---

## Key takeaways
1. Legacy code is evidence of past success, not past failure — judge the constraints, not the people.
2. Schedule pressure is not a valid reason to degrade code quality; treat "just this once" as a slippery slope.
